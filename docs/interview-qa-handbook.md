## 一、项目整体介绍（必考开场题）

---

### 📖 知识点精讲 1：Agent 与 Spring AI 的概念底座

**1. 什么是 AI Agent？与普通 LLM 应用的区别。**

- LLM 应用 = 用户提问 → 模型回答（一次请求一次响应，如 /chat 接口）
- Agent = **感知（接收任务）→ 决策（自主选择行动）→ 执行（调用工具/检索）→ 观察（根据结果决定下一步）** 的循环体。判断标准：模型是否拥有"自主选择行动路径"的能力
- 本项目的决策点：模型自主判断"这个问题查知识库？调余额工具？还是直接回答"——这就是 Agent 与问答机器人的分界线

**2. Spring AI 四大核心抽象（背下来，选型题通用）**

| 抽象接口         | 作用                                           | 项目中的实现                             |
| ---------------- | ---------------------------------------------- | ---------------------------------------- |
| `ChatModel`      | 对话模型统一接口                               | OpenAiChatModel（指向智谱）              |
| `EmbeddingModel` | 文本向量化统一接口                             | OpenAiEmbeddingModel（embedding-3）      |
| `VectorStore`    | 向量存取统一接口                               | SimpleVectorStore（内存，可换 PGVector） |
| `ChatClient`     | 高层链式调用入口（prompt/user/tools/advisors） | 各 Controller 注入使用                   |

**3. 协议兼容思想。** 智谱把自家接口"伪装"成 OpenAI 格式（OpenAI 兼容端点），因此复用 OpenAI 适配器只改配置。理解这条，"换模型厂商要不要改代码"这类问题就秒答。

**4. 项目分层架构（复盘索引）。**

```
src/main/java/com/bank/agent/
├── BankAgentApplication.java      启动类
├── controller/  ChatController（基础对话）RagController（摄取+RAG问答）AgentController（融合Agent）
├── tool/        BankTools（余额/利息）KnowledgeTools（知识库检索）
├── config/      RagConfig（向量库+落盘）AgentConfig（对话记忆）
├── guard/       GuardRail（输入护栏）
└── observation/ ObservabilityAdvisor（耗时/token观测）
```

复盘方法：对着这张表回忆"每个类是哪个阶段为什么写的"，面试讲架构时从这张图展开。

**易错点复盘**：Spring Boot 与 Spring AI 版本必须配套（Spring AI 2.0.x 硬编码依赖 Boot 4.1.x），文档说"支持 3.4/3.5"可能是过时信息——以 `mvn dependency:tree` 实测为准。

### Q1：介绍一下你的项目

**A（60 秒版本）：** 我做了一个企业级智能业务助手 Agent，以合规要求最严苛的金融场景做技术验证。技术栈是 Spring Boot 4.1 + Spring AI 2.0 + GLM 大模型。核心能力四块：① **Agentic RAG 知识库问答**——把检索封装成工具，由模型自主决策何时查库，回答带来源标注抑制幻觉；② **Function Calling 工具链**——查余额、算利息等业务工具，模型自主路由；③ **多轮会话记忆**——滑动窗口策略，支持指代词追问；④ **工程化底座**——SSE 流式输出、输入安全护栏、路径白名单、自研 Advisor 采集耗时与 token 成本。每个能力我都有对照实验或测试矩阵验证，比如同一个问题"有 RAG vs 无 RAG"的回答对比。

**追问预判——"项目有什么不足？"**：诚实列出三点并给方案：① 向量库用的是内存实现（开发够用），生产应迁 PGVector，因为我的业务代码只依赖 `VectorStore` 接口，切换只改配置；② 会话记忆是内存存储，重启丢失，应换 JDBC/Redis 实现；③ 未做检索质量评估集，上生产前要构造问题集做回归。

### Q2：为什么选 Spring AI？而不是 LangChain4j 或 Python 的 LangChain？

**A：** ① 我是 Java 后端背景，Spring AI 与 Spring Boot 生态（依赖注入、自动配置、Actuator 监控）无缝集成，团队上手成本最低；② Spring AI 的**模型可移植性**设计是决定因素——业务代码只依赖 `ChatModel`/`VectorStore` 等抽象接口，我实测换模型厂商只改两行配置；③ LangChain4j 生态在快速追赶，但 Spring 官方维护、文档与 Spring Boot 版本对齐更可信。Python 的 LangChain 不选是因为企业 Java 体系里引入 Python 服务会多一层跨语言运维成本。

### Q3：为什么接入智谱？怎么接入的？

**A：** 智谱提供 OpenAI 兼容端点（`https://open.bigmodel.cn/api/paas/v4`），所以我复用 Spring AI 的 `spring-ai-starter-model-openai` 适配器，只改 base-url 和模型名（chat 用 glm-4-flash，向量化用 embedding-3），**代码零改动**。这里有个踩坑经验：Spring AI 官方自带的智谱专用适配器最高只到里程碑版本（2.0.0-M4），没有跟进 GA，混用里程碑版和正式版有兼容风险，所以我选择 OpenAI 兼容方案。这体现了"协议兼容"的价值——换厂商等于换配置。

## 二、RAG 知识库（最高频章节）

---

### 📖 知识点精讲 2：RAG 全链路原理

**1. Embedding（向量化）的本质。**

- 把一段文本映射成一个高维浮点向量（embedding-3 是 2048 维），训练目标是"语义相近的文本 → 向量距离近"
- 相似度度量用**余弦相似度**（夹角越小越相似），而不是欧氏距离（对文本长度敏感）
- 关键推论：向量是"语义坐标"，检索就是"在语义空间里找邻居"——所以检索命中的是**意思相近**的内容，哪怕用词完全不同

**2. 五环节流水线（对照项目实现）。**

| 环节     | 项目实现                                                         | 关键文件                             |
| -------- | ---------------------------------------------------------------- | ------------------------------------ |
| ① 切分   | MarkdownDocumentReader 按标题结构化切分 + TokenTextSplitter 兜底 | RagController.load()                 |
| ② 向量化 | embedding-3（add() 内自动调用）                                  | 同上                                 |
| ③ 存储   | SimpleVectorStore.add() + 落盘 data/vector-store.json            | RagConfig.vectorStore()              |
| ④ 检索   | similaritySearch(SearchRequest.topK=3)                           | KnowledgeTools.searchBankKnowledge() |
| ⑤ 生成   | System Prompt 约束"仅依据资料回答" + 流式输出                    | AgentController.SYSTEM_PROMPT        |

**3. 元数据（Metadata）体系。** 每个 Document 携带键值对：Markdown 写入 `source=文件名`，PDF 自动带 `file_name` + `page_number`。用途：引用溯源（回答标注"依据：资料N"）、按来源删除（增量更新）、权限过滤。**元数据是 RAG 可信度与可维护性的地基**。

**4. 摄取即资产。** 向量是花 API 费用算出来的成果——所以本项目做了落盘持久化（摄取后 save、启动时 load，恢复零 API 成本）。这个"昂贵计算离线化、成果持久化"思想在 Redis 缓存、CDN 等场景完全同构。

**易错点复盘**：① 切分不是越小越好——块太小上下文碎、太大噪音多；② topK 不是越大越好——3 是精度与成本的平衡起点；③ 内存向量库重启即空，必须配持久化或生产级实现；④ path 参数直接拼路径会被 `../` 穿越（已用白名单目录修复）。

---

### Q4：什么是 RAG？为什么需要它？

**A：** RAG（检索增强生成）= 检索 + 生成，本质是"给模型开卷考试"。流程：文档切分成块并向量化存入向量库 → 用户提问时先检索最相似的 Top-K 块 → 把资料连同问题交给 LLM 生成回答。需要它的原因：① 大模型不知道企业私有数据，知识有截止日期；② 全部文档塞上下文超出窗口限制且成本高；③ 引用来源可降低幻觉。**项目实证**：同一个问题"稳盈90天理财起购金额"，无 RAG 的回答是"大概几千到几万元，建议咨询客服"（零信息），有 RAG 精准回答"1万元，以1000元整数倍递增"（带依据标注）。

### Q5：RAG 的完整链路分几步？

**A：** 五环节：**切分（Chunking）→ 向量化（Embedding）→ 存储 → 检索（Retrieve）→ 生成**。前三个是离线摄取（做一次），后两个在线（每次提问）。我的实现：Markdown 按标题层级结构化切分（语义完整）+ TokenTextSplitter 按 token 数兜底细切；向量化用智谱 embedding-3；检索 topK=3；System Prompt 约束"仅依据资料回答"。

### Q6：文档切分有哪些策略？怎么选？

**A：** 四种：① 固定长度切分（简单但可能截断语义）；② 重叠切分（相邻块保留 10%~20% 重叠，缓解边界信息丢失）；③ **结构化切分**（按标题/段落，语义完整，结构化文档首选）；④ 语义切分（用 embedding 判断语义断点，效果最好成本最高）。实践通常"结构化切分 + 固定长度兜底 + 适度重叠"。**项目实证**：我的金融知识库是 Markdown，用 `MarkdownDocumentReader` 按标题切，11 个段落每段语义完整，向量化后检索命中精准。

### Q7：检索不准确怎么优化？

**A：** 分四层定位：① **切分层**：调块大小、加重叠、换结构化切分；② **检索层**：调大 topK + 相似度阈值过滤噪声、**混合检索**（向量 + BM25 关键词双路召回）、**重排序**（Reranker 对候选精排）；③ **查询层**：查询改写、多路查询扩展；④ **数据层**：元数据过滤、清理脏数据。方法论上强调：**先建评估集量化（命中率/召回率），再定位哪层出问题**，不盲目调参。

### Q8：为什么不用 MySQL 存向量？

**A：** MySQL 能存（JSON/BLOB）但**检索不了**——向量检索核心是最近邻搜索（ANN），需要专门索引结构（HNSW 图、IVF 倒排）把暴力 O(N) 优化到近似对数级；MySQL 只能全表扫逐行算余弦相似度。选型依据三要素：数据规模（万级 vs 亿级）、运维成本（能否复用已有 PostgreSQL）、一致性要求。**金融企业务实首选是 PGVector**（PostgreSQL 插件，向量 + 业务数据一个库）；亿级向量选 Milvus/Elasticsearch。我的项目业务代码只依赖 `VectorStore` 接口，迁移只换依赖和配置。

### Q9：知识库文档更新后，向量库怎么增量更新？

**A：** 三种策略：① 全量重建（简单但慢，适合小库）；② **增量按需**（文档级 hash 比对，变更的文档先按 metadata 的来源删除旧向量再插入新向量）；③ CDC 流水线（文档存储变更事件驱动实时更新）。关键注意**幂等**：同一文档重复摄取会产生重复向量，浪费 Top-K 名额——入库前按来源先删后插。

### Q10：扫描件 PDF 怎么处理？

**A：** 先做**类型检测**（有无文字层——我的排查方法：看 PDF 内部 `/Font` 对象数量，扫描件为 0；或 Ctrl+F 搜索法）。扫描件是"图片合集"，需先 OCR（PaddleOCR/Tesseract）转文本再进 RAG 链路，OCR 置信度低的页面标记人工复核。工程上先统计扫描件占比再决定是否建 OCR 管道（成本收益权衡）。**项目实证**：我的学生手册 PDF 实测 85MB、0 个字体对象、纯图片构成，我给摄取接口加了空结果防御——返回"可能是扫描型 PDF 需 OCR"的人话提示而不是 500。

## 三、工具调用（Agent 核心）

---

### 📖 知识点精讲 3：Function Calling 协议细节

**1. 消息角色（Message Types）——理解工具调用协议的前提。**

| 角色      | 谁产生               | 项目对应                                  |
| --------- | -------------------- | ----------------------------------------- |
| System    | 开发者（人设与纪律） | AgentController.SYSTEM_PROMPT"星辰小助手" |
| User      | 用户                 | 用户的问题                                |
| Assistant | 模型                 | 回答文本 / 工具调用请求                   |
| Tool      | 程序执行工具后的结果 | BankTools 方法的返回字符串                |

工具调用 = Assistant 发出"调用请求"→ 程序执行 → 结果以 Tool 消息回传 → Assistant 基于结果继续。

**2. 工具如何"注册"给模型。** `@Tool` 注解的方法由 Spring AI 转成"工具说明书"（名称 + description + 参数的 JSON Schema）随请求发送。模型看到的是说明书，不是代码——**模型输出的是"我想调 getAccountBalance(customerName=张三)"这样的结构化意图，执行永远发生在你的 JVM 里**。

**3. description 的写法公式。** 触发场景（何时调用）+ 数据边界（何时不调用）+ 参数示例。写完自测方法：换着花样问十句话，看日志里工具是否被正确触发/正确忽略。

**4. Agentic RAG 的架构意义。** 检索从"固定流程步骤"降格为"工具之一"，带来三件事：闲聊零检索成本、上下文无噪声、新增能力只是加一个工具。这就是"Agent 编排"的雏形——**能力以工具为单位插拔，编排交给模型**。

**易错点复盘**：① 工具返回值是给模型看的字符串，不是给用户的——敏感信息在工具内脱敏后返回；② 模型会"脑补"参数（用户没说客户名它可能填"张三"），工具方法内必须校验参数；③ description 有误导会导致模型频繁误调用（写"何时不调用"很关键）。

---

### Q11：Function Calling 的完整流程？模型会执行我的代码吗？

**A：** 四步循环：① 应用把工具清单（名称、描述、参数 JSON Schema）随消息发给模型；② 模型判断需要时返回**结构化调用请求**（工具名 + 参数），不生成自然语言；③ 应用在自己进程里执行真正的 Java 方法；④ 结果作为 tool 消息回传，模型基于结果生成回答，需要则循环。**模型从不执行代码——它只点菜，执行者是我的程序**。这是安全边界：鉴权、审计、权限校验全在工具方法体内。**项目实证**：查余额回答"8888.50 元"是我的 Java 方法里的模拟数，模型编不出这个精确值；算利息"5万两年 1850 元"数学验证分毫不差——精确计算和私有数据必须走工具，模型心算不可靠。

### Q12：工具的 description 怎么写？为什么重要？

**A：** description 是**写给模型看的说明书**，模型靠它决定"何时调用、不调用"。要点：① 写清触发场景（"当用户询问账户余额…时调用"）；② 写清**负向边界**（"闲聊、查余额不要调用"——我的知识库工具就写了排除项）；③ 参数描述给出示例值。description 质量直接决定多工具路由的准确率。

### Q13：多个工具怎么路由？会误调用吗？

**A：** 一次请求可挂多组工具（`tools(obj1, obj2)`），模型按 description 自主选择，包括"都不调用"。我的四用例验证矩阵：产品问题→检索工具、查余额→余额工具、算利息→计算工具、纯闲聊→零调用。防误调手段：description 写清触发和排除场景、System Prompt 纪律、（生产）工具按用户角色下发白名单。

### Q14：什么是 Agentic RAG？和传统 RAG 的区别？

**A：** 传统 RAG：**每次请求无条件检索**注入上下文——适合纯知识问答，流程固定延迟可预测。Agentic RAG：**检索只是工具之一**，模型判断需要才调用——适合混合场景（有的问题查库、有的查实时数据、有的闲聊），避免无关检索的延迟与噪音，还支持多轮检索（换关键词再查）。代价：多一次模型往返的延迟成本，依赖模型路由准确性。生产建议：问题域单一用传统 RAG，能力混合的 Agent 用 Agentic RAG——**我两者都实现了，可以现场对比**。

## 四、多轮记忆

---

### 📖 知识点精讲 4：上下文窗口与记忆策略

**1. 为什么必须有"记忆"组件。** HTTP 请求本身无状态，模型 API 也是无状态的——它**不记得**上一轮说过什么。所谓记忆 = 每次请求前把历史消息重新放回消息列表。本质：**记忆不是模型的功能，是应用的工程**。

**2. 滑动窗口策略（本项目实现）。** `MessageWindowChatMemory` + `maxMessages(20)`：每个会话保留最近 20 条，超出丢弃最早的。为什么不能无限保留：① 上下文窗口有硬上限；② token 成本随消息数线性增长（每轮都重发全部历史）；③ 早期消息对当前问题往往贡献最小。

**3. Advisor 机制（Spring AI 的 AOP）。** `MessageChatMemoryAdvisor` 实现 `BaseAdvisor`：请求前（before）把历史注入消息列表，响应后（after）把本轮问答写入存储。Advisor 链按 `getOrder()` 排序依次包裹——我的 `ObservabilityAdvisor` 也实现同一接口（order 更小排最外层，计时覆盖全链路）。**写一个自定义 Advisor = 掌握 Spring AI 的扩展模型**。

**4. 会话 ID 的双重身份。** 功能上：隔离不同对话（同一 conversationId 的历史才互相可见）；安全上：必须绑定认证用户（服务端校验归属），否则 UUID 就是"别人的对话读取凭证"。

**易错点复盘**：① Advisor 是单例，**不能在实例字段里存请求级状态**（并发互相污染）——要用方法局部变量或请求上下文；② 2.0 必须显式传 conversationId（`ChatMemory.CONVERSATION_ID` 参数），不传会报错或串话；③ 我的观测日志最初把 System Prompt 全文当"问题"打印——取"问题"要过滤 `MessageType.USER` 取最后一条，不能直接 `getContents()` 聚合全文。

### Q15：多轮对话的记忆怎么设计？历史太长怎么办？

**A：** 分层：① **短期记忆**：滑动窗口保留最近 N 条（我用 `MessageWindowChatMemory`，maxMessages=20，超出丢弃最早的）；② **摘要压缩**：超出窗口的历史用模型生成摘要替换；③ **向量记忆**：历史向量化入库按语义检索注入；④ **结构化画像**：抽取关键事实存库。生产要点：记忆按**用户 + 会话双维度隔离**、持久化（重启不丢）、敏感信息脱敏。**项目实证**：同一会话第二轮问"**那它**90天后到期利息多少"，模型正确解析了指代词"它"=上一轮的理财产品——记忆回放生效的直接证据。

### Q16：会话 ID 怎么管理？有什么安全考虑？

**A：** 我的设计：前端生成 UUID 并在整个会话内复用，通过 advisor 参数显式传给记忆组件（Spring AI 2.0 强制显式传，消除了旧版隐式默认 ID 导致"串话"的坑）。安全考虑：会话 ID **不能作为权限凭证**——真实系统必须先认证，把会话绑定到用户身份（服务端校验"这个用户只能访问自己的会话"），否则任何人拿到的 UUID 都能读别人的对话历史。

## 五、安全护栏

---

### 📖 知识点精讲 5：LLM 应用的安全分层

**1. 防线位置哲学——"程序层 > 提示词层"。**
提示词里写"绝不编造"是**软约束**，可以被"忽略之前的指令"这类注入攻击绕过；程序层的 if 判断、白名单、权限校验是**硬约束**，模型无法绕过。设计原则：提示词做第一道柔性引导，程序做刚性边界。

**2. 护栏插在哪个位置（对照项目实现）。**

| 位置               | 防什么                           | 项目实现                                      |
| ------------------ | -------------------------------- | --------------------------------------------- |
| 输入侧（进模型前） | 超长输入（token 攻击）、违规意图 | `GuardRail.check()`：长度 500 上限 + 敏感词表 |
| 摄取侧（读文件前） | 路径穿越读任意文件               | 白名单目录 normalize + startsWith + 扩展名    |
| 工具内（执行时）   | 异常参数、越权                   | 方法体内校验（不信任模型给的参数）            |
| 输出侧（进模型后） | 敏感内容外泄                     | 本项目由 System Prompt 约束，生产需 DLP 扫描  |

**3. 提示词注入的直观理解。** 你的 System Prompt 和用户输入最终拼成同一段文本发给模型——模型天然无法完全区分"指令"和"数据"。缓解手段：输入护栏、指令与数据用分隔符隔离、工具权限最小化（即使被注入也调不了危险操作）、输出审查。

**4. Fail Fast + Fail Friendly。** 致命配置（密钥缺失）启动即失败；可解释的异常（扫描件无文字层）返回"原因 + 建议"而不是 500 堆栈。两者都是对使用者的尊重。

**易错点复盘**：① 修安全代码后必须跑全量回归——我修路径白名单时把 path 语义改了（项目根 → docs/knowledge 相对），默认摄取路径当场失效，被回归用例抓出；② 敏感词表是粗筛，误杀率需要监控，生产应接内容安全 API；③ 拒绝话术要给出路（"请拨打 95577"），用户体验和安全不冲突。

### Q17：LLM 应用有哪些特有安全风险？你防了哪些？

**A：** 按 OWASP LLM Top 10 挑重点：① **提示词注入**（LLM01）：用户输入"忽略以上指令"诱导越权——我的防线是**程序级护栏**（敏感词 + 长度限制在进入模型之前拦截），加上工具权限最小化（模型只能调白名单工具，鉴权在方法体内）；② **敏感信息泄露**（LLM06）：System Prompt 和知识库可能被套出——回答边界由 System Prompt 约束，生产需输出 DLP 扫描；③ **供应链**（LLM08）：密钥走环境变量不进代码库。**核心观点：模型层防线（提示词）永远可能被绕过，真正的安全边界必须在程序层**——这句话体现工程成熟度。

### Q18：路径穿越攻击是什么？怎么防？

**A：** 攻击：接口参数传 `../../pom.xml` 或绝对路径，读取服务器任意文件。防御三件套：`normalize()` 路径规范化 + `startsWith(baseDir)` 白名单目录校验 + 扩展名白名单。更稳的语义设计：**path 参数只允许白名单目录内的相对路径**，目录前缀由服务端拼接。**项目实证**：我实测拦截了 `?path=../../pom.xml`，且回归测试发现护栏修复本身引入过"默认路径失效"的 BUG——**改安全代码必须跑全量回归**。

### 📖 知识点精讲 6：SSE、响应式与依赖管理

**1. SSE 协议格式（能手写出来就是加分）。**

```
HTTP/1.1 200 OK
Content-Type: text/event-stream;charset=UTF-8

data:第一段文本

data:第二段文本

```

- 每条事件以 `data:` 开头，事件之间用**空行**分隔；流不关闭，服务器可一直推送
- 浏览器消费：`fetch` → `resp.body.getReader()` → `TextDecoder('utf-8', {stream:true})` 解码 → 按 `\n\n` 切分 → 去掉 `data:` 前缀追加到 DOM（chat.html 完整实现）

**2. 为什么 UTF-8 声明踩坑。** `produces` 里写 charset 会被 Spring 的 SSE 输出路径剥离（SSE 规范强制 UTF-8）；要控制响应头必须用 `ResponseEntity.contentType(new MediaType("text","event-stream",StandardCharsets.UTF_8))`。浏览器直接打开 SSE 端点时若头里无 charset，会按 windows-1252 误读 → 中文变 `å¤§å­˜å•`（实测复现）。**排查技巧：`document.characterSet` 看浏览器实际用的编码。**

**3. Reactor 最小知识集。** `Flux<T>` = 0..N 个元素的异步序列；`doOnNext`（逐元素处理）/ `doFinally`（流终结时执行，无论正常/异常/取消）；流式 token 用量随最后一个 chunk 到达 → 用 `AtomicReference` 记录最后一个有效值，`doFinally` 打印。

**4. Maven 依赖调解与排查工具箱。**

- 冲突表现：`NoSuchMethodError`/`ClassNotFoundError`/Bean 重复定义
- 工具：`mvn dependency:tree -Dincludes=组名` 定位版本混杂；读 `~/.m2/repository/.../xxx.pom` 看传递依赖的真实声明；`mvn clean compile` 消除 IDE 与 Maven 的坏 class 竞态
- 修复优先级：对齐版本 > exclusion 排除 > （万不得已）allow-bean-definition-overriding
- **项目实证**：Spring AI 2.0.1 starter 硬编码 Boot 4.1.1 模块，配 Boot 3.5.3 启动即报 Bean 冲突——升级对齐解决

**5. Spring 自动配置原理（一句话版）。** 启动时读取各 jar 的 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，按 `@ConditionalOnClass/@ConditionalOnMissingBean` 条件装配——所以引入 starter 就"凭空"出现 `ChatModel`、`ChatClient.Builder` 等 Bean。注意：**@Bean 方法声明的返回类型 = 容器里的 Bean 类型**（我声明接口 VectorStore 后按 SimpleVectorStore 注入就失败）。

**6. 环境变量进程继承链。** 终端 → mvn → JVM 逐级继承；永久环境变量只在**新启动的进程**可见（老窗口/老 IDE 永远读旧值）。密钥管理遵循十二要素：`${ENV_VAR}` 占位符 + 不进代码库。

### Q19：流式输出怎么实现的？为什么选 SSE 不选 WebSocket？

**A：** SSE（Server-Sent Events）是基于 HTTP 的单向推送协议，响应类型 `text/event-stream`。选型理由：① 对话是"请求一次 + 流式响应"，SSE 的单向模型刚好匹配；② 纯 HTTP，复用现有网关鉴权/负载均衡，WebSocket 需协议升级额外配置；③ SSE 自带断线重连语义。**实现细节与坑**：后端用 Spring AI 的 `Flux<String>` 流式 API + `ResponseEntity` 显式声明 `charset=UTF-8`（坑：`produces` 写 charset 会被 Spring 的 SSE 输出路径剥离，导致浏览器直接访问时按 windows-1252 误读中文——我实测复现并修复）；前端 `fetch` + `ReadableStream` + `TextDecoder` 流式解码，必须用 `{stream:true}` 模式处理"一个中文字被拆到两个数据块"的截断问题，并按 `\n\n` 切分 SSE 事件缓存不完整片段。

### Q20：Agent 上线后如何监控？

**A：** 四层：① **业务指标**：问答成功率、拒答率、工具调用分布、单次问答 token 成本；② **性能指标**：**首 token 延迟（TTFT，流式体验关键）**、总耗时 P95/P99；③ **质量指标**：评估问题集定期回归（检索命中率、引用准确率）；④ **告警**：模型 API 错误率/限流、向量库不可用。**项目实证**：我自研了一个 `ObservabilityAdvisor`（Spring AI Advisor 链本质是 AOP）记录每次问答的问题、耗时、token 用量和工具调用日志，实测数据形如"耗时 2987ms、提示 1212 tokens、生成 28 tokens、总 1240 tokens"。生产化升级：接 Micrometer + Actuator 自动埋点 `gen_ai.*` 指标。

### Q21：讲一次你排查依赖冲突的经历

**A（真实案例，证明实战能力）：** 我的项目启动报 `jsonComponentModule` Bean 重复定义——两个不同包路径的 `JacksonAutoConfiguration`。解读：包路径分属 Spring Boot 3.x 和 4.x，说明 classpath 混入两个大版本。排查：① `mvn dependency:tree -Dincludes=org.springframework.boot` 看版本混杂 → 发现 `spring-ai-starter-model-openai:2.0.1` 传递引入了 `spring-boot-starter-webclient:4.1.1`；② 读本地仓库里该 starter 的 pom，确认它**硬编码**依赖 Boot 4.1.1（官方文档却写着"支持 3.4/3.5"，已过时）。修复：升级 Spring Boot 到 4.1.1 对齐（而非降级或开 `allow-bean-definition-overriding` 掩盖问题）。**经验教训：AI 时代的框架文档可能滞后，以依赖树和仓库实际字节为准。**

### Q22：按类型注入 Bean 报错（NoSuchBeanDefinitionException）怎么排查？

**A：** 常见原因：① **@Bean 方法声明返回类型 = 容器中的 Bean 类型**——我真实踩过：方法声明返回接口 `VectorStore`，注入实现类 `SimpleVectorStore` 报 Bean not found（Spring 按方法声明类型注册类型元数据，不看运行时实际类型），修复是声明具体类型；② Bean 不在组件扫描范围；③ 条件注解未满足；④ 多候选未指定 `@Primary/@Qualifier`。工具：Spring 启动失败的 FailureAnalyzer 会直接说"哪个类的哪个参数需要什么 Bean"。

### Q23：配置错误的处理原则？

**A：** **Fail Fast + Fail Friendly**：致命配置（密钥缺失）应在启动阶段拒绝启动而不是等到第一个请求；检测到无法处理的输入时返回"原因 + 可操作建议"而不是堆栈。**项目实证**：我遇到过环境变量没生效时占位默认值"请设置环境变量…"被当真密钥发出、在 HTTP 头校验时报 `Unexpected char 0x8bf7`（0x8bf7 就是"请"字的 Unicode 码点）——这个案例说明：① 占位默认值会把配置错误延迟到运行时（应启动即校验）；② 环境变量沿"终端→mvn→JVM"进程链继承，链上任何老进程都读不到新变量。

### Q24：密钥为什么不能写配置文件？生产怎么管？

**A：** ① 配置文件进 Git，密钥随历史记录永久泄露；② 十二要素应用原则：配置与代码分离，环境变量注入，一套代码多环境部署。Spring 的优先级：命令行参数 > JVM 系统属性 > **环境变量** > profile 配置 > application.yml。进阶：配置中心（Nacos）、Vault/Jasypt 加密。我的项目用 `${ZHIPUAGENT_API_KEY:默认提示}` 占位符，多项目共存时变量名加前缀区分。

### 📖 知识点精讲 7：从 Demo 到生产的距离

**1. 生产化 Checklist（按优先级）。**

```
鉴权与会话绑定（用户体系） → 存储（PGVector/Redis） → 评估集与回归
→ 异步任务化（摄取/长任务） → 高可用（限流重试/多实例） → 成本治理（缓存/路由）
```

面试策略：主动承认"我现在是 demo 完成度"，但**每一条都说得出为什么没做和生产做法**——暴露认知短板远好于假装完美。

**2. Token 成本模型（能算账就是懂行）。**

- 计费 = 输入 token + 输出 token（输出单价通常是输入的 2~4 倍）
- 多轮对话的隐性成本：**历史每轮都重发**，对话越长每轮越贵——这就是窗口记忆（maxMessages=20）存在的经济理由
- 优化三板斧：提示词缓存（Prompt Caching）、压缩检索资料条数、简单问题路由到轻量模型
- **我的实测数据**：单次问答总 1240 tokens，其中提示占 1212（97.7%）——结论：优化重点在压缩提示词，而不是担心输出长度

**3. 评估（Evaluation）最小方案。** 构造 30~100 条"问题 + 标准答案 + 出处"的评估集 → 脚本批量调用 → 断言答案包含关键事实（如"1万元"）→ 统计命中率。每次改切分参数/换模型/改提示词后回归。没有评估的 RAG 调优 = 盲调。

**4. 首 token 延迟（TTFT）。** 流式体验的核心指标：用户从发出请求到看到第一个字的时间。恶化原因：检索慢、模型排队、System Prompt 过长。我的观测 Advisor 记录了总耗时，生产版应拆分 TTFT 与生成耗时分别打点。

### Q25：你这个项目离生产还差什么？（考自我认知）

### 📖 知识点精讲 9：RAG 两层评估体系

| **生成层** | 完整 Agent 链路的最终回答           | 调 LLM（慢 + 随机性） | `RUN_LLM_EVAL=true` 显式开启（`RagAnswerEvaluationTest`） | **80%~87%**（波动，边缘用例受模型随机性影响） |

**3. 评估集设计（EvalDataset.java，15 例）。**

- **事实型**（10 条）："三年定期利率"→断言含 "2.20%"——断言**关键事实片段**而非完整句子，容忍表达差异、锁定事实底线
- **对比型**（1 条）："90天和365天哪个门槛低"——需同时召回两段资料
- **无答案型**（2 条）："怎么办理护照"→断言**拒答**（"没有相关/无法"类表达）
- 问题措辞刻意与知识库原文不同——测**语义检索**而非关键词匹配

**4. 评估驱动修复的三真实案例（评估一次跑出三个问题）。**

- **断言误判**：期望 "20 万元"（知识库原文带空格），模型转述 "20万元"（省空格）——6 条"正确却 FAIL"。修复：断言前**空格归一化**。教训：LLM 评估的头号误判源是表达差异，不是事实错误
- **单位转述错误**：问"房贷能贷几成"，模型答"房价的**70成**"（数字对单位错）。修复：知识库原文改为"七成（即 70%）"双表述——**数据质量决定 RAG 质量**
- **拒答失效**：模型对知识库没有的问题（办护照）凭通用知识作答。修复：System Prompt 增加第 0 条"产品问题必须先检索"。遗留：拒答仍偶发失效（temperature 随机性），生产应加输出侧校验

**5. 已知遗留（诚实记录）。** E13 对比型问题检索 MISS（topK=3 无法同时召回两段资料，优化方向：查询改写/调大 topK）；拒答偶发失效。**遗留不是缺陷隐藏，而是记录在案的优化清单**。

### 📖 知识点精讲 10：MCP——工具生态的开放标准

**1. MCP 是什么。** Model Context Protocol，Anthropic 推出的 AI 工具接入开放标准（JSON-RPC 2.0 over SSE/STDIO），统一"AI 应用 ↔ 工具提供方"协议。价值：工具一次开发，任何 MCP 客户端（Cursor、Claude Desktop、其他 Agent）零改造接入——**从应用私有变为生态公共**。

**2. 与 Function Calling 的关系（易混淆点）。** FC 是**模型↔应用**之间的调用机制（模型决定调什么）；MCP 是**应用↔工具生态**之间的标准化协议（工具如何被发现和调用）。二者互补：我的 Agent 内部用 FC 调工具，同时把这些工具通过 MCP 暴露给整个生态。

**3. 握手流程（本项目完整实测）。**

```
① GET /sse                    → 服务器推送 event:endpoint + sessionId（建立会话）
② POST /mcp/message?sessionId → initialize（协议版本/能力协商）
③ POST notifications/initialized
④ POST tools/list             → 返回 3 个工具（名称/描述/JSON Schema 参数定义）
```

实测响应片段：`serverInfo: {"name":"bank-agent-mcp","version":"0.0.1"}` + 三个工具的完整定义——名称和参数 Schema 由 @Tool 注解自动生成。

**4. 双通道注册（踩坑实录）。** Spring AI 的 MCP 自动配置有两条工具收集路径：① 注解扫描器（扫容器中带 @Tool 方法的 **Bean**）；② 容器中的 `ToolCallbackProvider`。踩坑：工具类只 `new` 不进容器时，扫描器发现不了（日志 "No tool methods found in the provided tool objects: []"）。最终方案：**工具类注册为 Spring Bean + MethodToolCallbackProvider 显式收集**双保险，日志确认 `Registered tools: 3`。

**易错点复盘**：① 工具类必须进 Spring 容器（new 出来的对象扫描器看不见）；② 用 PowerShell 发 JSON 测试时 `-Encoding UTF8` 会写 BOM 头导致服务端 "Invalid message format"——ASCII 编码解决；③ `GET /sse` 是长连接，验证时用 curl `-m` 限时 + 后台读输出文件。

### Q27：你的 AI 项目怎么写测试？模型输出不确定怎么断言？

**A：** 分层策略：① **纯逻辑单测**（护栏/工具计算/检索格式化）：确定性输出，JUnit 直接断言——我的项目 26 个单测全绿；② **依赖隔离测试**：Mockito mock 向量库/模型依赖，验证"应用把正确的请求发出去、正确解析返回"（用 ArgumentCaptor 验证用户问题真的传给了检索组件）；③ **LLM 输出断言技巧**：不断言全文，断言**关键事实包含**（答案必须含"1万元"）、来源标注存在、拒答触发——容忍表达差异、锁定事实底线；④ **评估集回归**（见 Q28）：批量验证端到端质量。核心观点：**把确定性部分 100% 测起来，把不确定性部分用评估集管起来**。

### Q28：你怎么证明 RAG 系统的质量是可靠的？

**A：** 我建了**两层评估体系**：① 检索层（离线、免费、每次调整必跑）：15 例评估集断言 topK 命中率，当前 100%（13/13）；② 生成层（走完整 Agent 链路，显式开关）：断言关键事实与拒答率，80%~87% 波动（边缘用例受模型随机性影响）。评估集分三类：事实型、对比型、无答案型（专门测拒答）。**这套体系上线后就是回归防线：任何提示词/参数/模型变更先过评估再上线**。加分点：讲一个评估抓出真实缺陷的案例——我的评估跑出"房贷额度回答 70成"，根因是知识库只写"70%"而模型做"几成"单位转换出错，靠知识库双表述修复；还有 6 条"回答正确却 FAIL"的断言误判（模型省略空格），靠断言归一化修复——**区分"断言问题"和"真实缺陷"是评估体系建设的第一课**。更进阶的一课：对比型用例 E13 长期 MISS，最初归因"topK 不足"，调大窗口无效；给评估加了 MISS 诊断打印（召回内容可视）后发现 top5 全是同一条文档——真因是评估测试每次启动重复摄取，重复主题占满检索窗口把另一主题挤出。**修复评估基础设施的污染后检索层直接 100%——评估工具本身也需要被审计**。

### Q29：MCP 是什么？你的项目怎么用？

**A：** MCP（Model Context Protocol）是 AI 工具接入的开放标准（JSON-RPC over SSE/STDIO），统一"AI 应用 ↔ 工具提供方"协议。我的项目用 Spring AI 的 MCP Server starter 把银行工具（查余额/算利息/知识库检索）暴露为标准 MCP 服务，完整实现握手：客户端 GET /sse 建会话 → initialize 协商 → tools/list 获取 3 个工具（含中文描述与 JSON Schema 参数）。价值：Cursor、Claude Desktop 等客户端零改造调用我的工具。**与 FC 的关系**：FC 是模型↔应用的调用机制，MCP 是应用↔工具生态的标准协议，互补而非替代。踩坑点：工具类必须注册为 Spring Bean（只 new 不进容器，MCP 扫描器发现不了）。

### Q30：讲一次你写测试或做验证时的踩坑经历

**A（三选一，按面试官兴趣）：**

- **Mock 教训**：测试 KnowledgeTools 时构造真实向量库 + mock EmbeddingModel，报 "Vectors must not be null"——store 内部调用链与 stub 不匹配。领悟：mock 依赖本身而非实现细节，单测只测自己这层；全链路交给评估体系
- **坏 class 排查**：运行时报 "Unresolved compilation problem"——IDE 编译器在有错误的源码上生成坏 class，Maven 增量编译因时间戳跳过重编译。`mvn clean test` 解决。经历两次后形成习惯：诡异运行时错误先 clean
- **评估误判**：6 条"回答正确却 FAIL"——期望"20 万元"模型写"20万元"。教训：评估断言必须归一化（去空格/统一格式），区分"断言问题"与"真实缺陷"，否则会错误地"修好"本来正确的系统
- **评估污染（最推荐讲）**：对比型用例 E13 长期 MISS，直觉归因"topK 不足"，调大无效；加 MISS 诊断打印（打印召回内容）后发现 top5 全是同一条文档——真因是评估测试每次启动**重复摄取**，同一主题的重复副本占满检索窗口，把另一主题挤出。修复摄取幂等性（落盘文件存在则跳过）后 13/13 全绿。教训：①"没有日志的失败只能靠猜"，诊断信息要内建在评估里；② 评估基础设施自身也会说谎，先审计测量工具再优化被测系统；③ 错误归因差点导致一次无意义的"动态 topK"过度设计

## 九、Agent 能力进阶（多步 ReAct / 反思循环 / 长期记忆）

### 📖 知识点精讲 11：ReAct——推理与行动交替的 Agent 执行模式

**ReAct = Reasoning + Acting**：模型不一次性给出最终答案，而是循环执行"**思考 → 调工具 → 观察结果 → 再思考**"，直到信息足够才收敛作答。关键认知：

- **Spring AI 把 ReAct 循环内置在框架里**：调用 `.tools(...)` 后，框架自动处理"模型请求工具 → 执行工具 → 回填结果 → 再次请求模型"的循环，开发者只写工具本身。所以我的代码里没有显式 while 循环——循环藏在 `.stream()` 内部
- **单步 FC vs 多步 ReAct 的分界**：问"查余额"是单步（1 次工具调用 1 轮回答）；问"1 万存三年定期 vs 稳盈 90 天哪个划算"需要**跨工具编排**（算定期利息 → 检索理财规则 → 算理财收益 → 对比），这是真正的 Agent 行为
- **能力光谱定位**（面试表达框架）：我的项目是"**支持多步 ReAct 编排的工具增强型 Agent**"，不是全自主智能体（没有自主规划子目标、没有长期任务队列）——主动说清边界比夸大更得分

### 📖 知识点精讲 12：反思循环（Evaluator-Optimizer 模式）

单次生成质量不稳定（漏答要点、数字算错），反思循环加一道**质量闸门**：

```
生成（Generator）→ 评审（Evaluator，给分+找缺陷）→ 不达标则带着反馈修正（Revise）→ 循环直到达标或到轮次上限
```

- **评审者要比生成者"信息更足"**：我的评估者挂了知识库检索工具，能核对答案里的数字是否与知识库一致——生成者只凭上下文答题，评审者可以查证
- **结构化输出**：评审结果用 `.entity(ReviewResult.class)` 强制成 JSON（score + issues 列表 + passed 标志），代码拿到的是对象而不是自由文本，避免"解析模型口语"的脆弱性
- **工程防御**：修正上限 2 轮（防死循环烧钱）；评审环节异常**降级为通过**（评审挂了不能把主流程挂掉）
- **实测数据**：多步对比任务第 1 轮评审 5 分、抓出 3 个缺陷（漏定期利率、漏风险等级）→ 第 2 轮修正 8 分全过——这就是面试里"反思循环真实有效"的证据

### 📖 知识点精讲 13：Agent 记忆分层——短期记忆 vs 长期记忆

| 维度     | 短期记忆（会话记忆）               | 长期记忆（用户画像）           |
| -------- | ---------------------------------- | ------------------------------ |
| 隔离键   | conversationId（会话）             | userId（用户）                 |
| 内容     | 原始对话消息（user/assistant）     | LLM 抽取的结构化事实           |
| 载体     | MessageWindowChatMemory 窗口 20 条 | 内存 Map（生产换 DB/Redis）    |
| 注入方式 | Advisor 自动回放历史消息           | 拼进 System Prompt             |
| 生效范围 | 同一会话内                         | 跨会话（换会话 ID 依然记得你） |

**写入侧设计**：不是把对话原文存下来，而是对话结束后用**另一次 LLM 调用做事实抽取**（结构化输出 `{"facts": [...]}`，规则：只抽用户明确表达的、禁止推测、与已有画像去重、无新事实返回空数组）——画像存的是"用户风险偏好为低风险"这种**浓缩事实**，而非聊天记录。

**读取侧设计**：生成前召回画像拼进 System Prompt，措辞用指令式（"该用户已确认的信息——必须直接遵循，严禁再次询问"），无画像时返回空串不污染提示词。

### Q31：你的 Agent 能自主多步执行吗？怎么证明？

**A：** 能。我设计了一个**必须跨工具才能完成的任务**："1 万存三年定期和稳盈 90 天哪个划算"。这个问题模型无法一次回答——它自主完成了编排：调用定期利息工具（算出 660 元）→ 检索知识库拿理财规则 → 调用理财收益工具（算出 70.27 元）→ 统一换算成年化口径对比作答。日志里能看到连续 3 次工具调用。**验证方法值得强调**：不是"看起来智能了"，而是检查每一步的数值正确性——我实际发现模型把理财收益心算错（77.75 vs 精确 70.27），根因是没有专用计算工具，补上 `calcWealthManagementReturn` 工具后复测精确。这个"发现缺陷 → 定位根因 → 修复 → 复测"闭环就是工程化验证。

### Q32：什么是反思循环？为什么需要它？

**A：** 单次 LLM 生成质量有方差（漏要点、数字错），反思循环用 **Evaluator-Optimizer 模式**加质量闸门：生成后由另一个评审角色打分并找缺陷，不达标就带着反馈修正，上限 2 轮。我的实现有三个细节：① 评审者挂知识库工具能**查证**数字（比生成者信息更足）；② 评审结果用结构化输出（entity 强制 JSON），拿到的是 ReviewResult 对象而非自由文本；③ 评审异常**降级为通过**——评审是增强不是依赖，它挂了主流程不能挂。实测：第 1 轮评审 5 分抓 3 缺陷，第 2 轮修正后 8 分全过。**代价也要主动说**：每轮多 2 次 LLM 调用，延迟翻倍，适合对准确性敏感的金融场景，不适合闲聊。

### Q33：跨会话长期记忆怎么实现？和短期记忆什么区别？

**A：** 核心是**隔离键和内容形态都不同**：短期记忆按 conversationId 存原始消息（窗口 20 条），长期记忆按 userId 存 LLM 抽取的结构化事实。实现三步：**抽取**（对话结束后另起一次 LLM 调用，结构化输出事实数组，去重合并、上限 20 条防膨胀）、**存储**（userId → 事实列表，我用内存 Map 教学，生产换 DB/Redis）、**注入**（下次请求召回画像拼进 System Prompt，指令式措辞"严禁再次询问"）。验证用三段式：会话 A 自我介绍写入画像 → 换全新会话 ID 提问，模型直接"根据您低风险偏好推荐 R2 产品"不再反问 → 换无画像用户对照，得到通用推荐。**当前局限主动讲**：内存存储重启即丢，这正是迁移 PostgreSQL 的动机。

### Q34：讲一次"记忆功能明明注入了却不生效"的排查经历

**A（STAR 结构）：** 这是我项目里最有价值的调试经历。**现象**：会话 B 已注入用户画像（低风险偏好），模型回答时仍反问"您的风险偏好是什么"。**定位**：在注入点加诊断日志，铁证召回数=1、注入内容完整——工程链路正确。**假设**：是模型能力问题而非工程问题。**验证**：把模型从 glm-4-flash 临时切到 glm-4-plus 复测——同一份注入代码，plus 直接按画像推荐、不再反问。**结论**：长期记忆的瓶颈不在"记住"（注入是确定性的），而在小模型对提示词约束的**遵循度**。顺手补了可观测性缺口：抽取环节原本成功/失败/空结果三个出口都无日志（静默失败不可区分），加入口+结果+堆栈三类日志。**面试落点**：① 分层选型结论——小模型跑工具循环控成本，强模型跑个性化/评审保质量；② "先证明工程对、再证明模型弱"的排查方法论；③ 模型遵循度是概率性的，强约束别只靠提示词，关键规则该上代码校验就上代码校验。
